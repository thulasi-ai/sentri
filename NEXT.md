> INT-002 ✅ shipped in PR #15 (GitHub App-based Check Run client `backend/src/integrations/githubChecks.js` with TTL-cached installation tokens + bounded retry / `Retry-After` honouring; `queued → in_progress → success/failure/neutral` lifecycle wired in `routes/trigger.js`; HMAC-verified `POST /trigger/github` endpoint with event filtering; `X-GitHub-Delivery` UUID idempotency via cross-dialect `LIKE`-based `findByGithubDeliveryId` lookup — Postgres-safe; regressed-tests-only summary with explicit "no green base" fallback (25-run lookback bound in `runResultFormatters.js`); Web Vitals violations as a separate markdown bullet; per-project Settings → Integrations tab opt-in toggle with admin-write / qa_lead-read gates; `concludeGithubCheck` runs in `onComplete` AFTER `runRepo.save()` and swallows GitHub 5xx so a provider outage never fails the underlying Sentri run; lean accessor `getRecentTestRunsForGithubBase()` for the base-run lookup avoids deserialising heavy JSON blobs on every check completion). Promoting AUTO-004 as previously queued — the file-level diff signal is the natural extension of AUTO-001's risk scorer and AUTO-002's `changedPages[]` baseline, and the GitHub webhook plumbing landed by INT-002 already carries the `pull_request.head.sha` we need to hit GitHub's PR-files API.
Today Sentri runs every approved test on every CI trigger. With AUTO-002's baseline mechanism in place and AUTO-001's risk scorer consuming `changedPages[]`, the next step is mapping file-level git-diffs to affected tests: when a PR touches `src/checkout/CartPage.tsx`, only the tests whose crawl snapshots include elements from that component should run. This is the "smart subset" that makes Sentri viable on large suites where running the full regression on every push is prohibitive. The mapping is built by cross-referencing each test's `sourceUrl` + captured elements against the file paths extracted from the git diff (via GitHub's PR files API, already available on the INT-002 webhook path), then unioning the file→URL mapping with AUTO-002's `changedPages[]` signal and feeding the union into AUTO-001's scorer as an additional file-affinity boost term.
**Implementation sketch:**
- New `backend/src/pipeline/impactAnalysis.js` (pure function: `{ changedFiles: string[], testsWithSnapshots: Test[] } → { affectedTests: Test[], unknownFiles: string[] }`). No DB access — callers pass in everything. Mirrors the `riskScorer.js` shape per AUTO-001's precedent.
- `backend/src/integrations/githubChecks.js`: new `getChangedFilesForPr({ repo, prNumber, installationId })` reusing the existing installation-token cache + bounded-retry / `Retry-After` fetch wrapper. Calls `GET /repos/:owner/:repo/pulls/:number/files` (paginated, capped at 300 files — GitHub's default page-1 limit is 30 and the API caps at 3000).
- `backend/src/routes/trigger.js`: when the GitHub webhook delivery has `pull_request.number` (already normalised by `normalizeGithubPayload`), fetch `changedFiles[]` via the new helper, plumb into impact analysis, and pass the resulting affected-test set as an *additional* filter on top of AUTO-001's risk ordering. Body-level `changedFiles[]` override is accepted from non-GitHub CI callers (Jenkins / GitLab / generic) so the feature works without a GitHub App connection.
- `backend/src/pipeline/riskScorer.js`: new optional `fileAffinityBoost` weight (additive, default `+25` for a file-affected test). Mirrors the `changedPages` boost path so the two signals compose — a test that's both DOM-changed AND file-affected surfaces at the very top.
- `frontend/src/pages/RunDetail.jsx`: new "Impact scope" panel listing the changed files that drove the test selection (collapsible, hidden when `changedFiles` is empty / absent so legacy runs render identically).
- New `backend/tests/impact-analysis.test.js`: file→URL mapping correctness; empty-diff fallback to full suite + AUTO-001 ordering only; unknown-file graceful degradation (`skipped_no_impact` semantics — never silently run the full suite when the diff was "config-only"); merge with `changedPages[]` from AUTO-002.

  **Files:** new `backend/src/pipeline/impactAnalysis.js` · `backend/src/integrations/githubChecks.js` (add `getChangedFilesForPr`) · `backend/src/routes/trigger.js` (plumb `changedFiles` into the risk path; accept body override) · `backend/src/pipeline/riskScorer.js` (file-affinity boost, additive to existing weights) · `backend/src/database/repositories/runRepo.js` (add `changedFiles` to `JSON_FIELDS` + `INSERT_COLS`) · new migration `022_run_changed_files.sql` · `frontend/src/pages/RunDetail.jsx` (Impact scope panel) · new `backend/tests/impact-analysis.test.js` (registered in `run-tests.js`) · `docs/changelog.md` (`### Added` entry)

### 1 · CAP-001 — Data-driven testing (parameterized iterations)
**Effort:** M | **Priority:** 🟢 Differentiator | **Dependencies:** none | **Source:** `ROADMAP.md` Phase 4 (CAP-001)
Generated tests are single-shot — one assertion path, one input set. Industry-standard practice (Cypress, Playwright `test.describe.serial` + fixtures, Mabl iterations) is to run the same test against N data rows from a CSV / JSON fixture, with one Run row per iteration so failures are attributable to a specific row. Sentri has no fixture concept today, so testing edge-case data combinations means hand-authoring N near-identical tests. Add per-test fixture upload (CSV / JSON) stored as a `test_fixtures` table row; extend the runner to iterate over fixture rows when present, substituting placeholders in `playwrightCode` (e.g. `{{email}}` → row value).
**Files:** new migration — `test_fixtures` table keyed on `(testId, version)` with `format` (`"csv"` | `"json"`), `rows` (TEXT JSON), `createdAt` · new `backend/src/database/repositories/testFixtureRepo.js` · `backend/src/runner/executeTest.js` (iterate over fixture rows, emit per-iteration result rows with `iterationIndex`) · `backend/src/routes/tests.js` (`POST /api/v1/tests/:testId/fixtures` upload, `GET …/fixtures` list) · `backend/src/middleware/permissions.json` (qa_lead+ on mutations) · `frontend/src/pages/TestDetail.jsx` (fixture upload + preview) · `frontend/src/components/run/StepResultsView.jsx` (per-iteration sub-table) · `backend/tests/fixture-iteration.test.js`

**Acceptance criteria:**
- Uploading a 5-row CSV fixture to a test produces 5 iteration results on the next run, each with an `iterationIndex` field.
- Per-project iteration cap (default 10, max 100) so a 10k-row CSV can't exhaust the worker pool.
- Tests without fixtures behave identically to today (single iteration, no sub-table) — zero regression.
- Failed iterations are attributable to a specific row (`iterationIndex` + row snapshot in the result payload).
